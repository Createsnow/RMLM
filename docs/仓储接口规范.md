# 研发物料管家 RMLM · 仓储系统接口规范 v1

本规范由 RMLM 拟定，**由仓储系统实现、RMLM 调用**。共两个接口：查询条码、拆分申请新码。

## 一、背景与分工

- 实物条码由仓储系统统一赋码，RMLM 不再自己发码，只引用仓储条码。
- 条码可能是**一件一码**（如一卷光缆一个码），也可能是**一批一码**（如一袋 50 个插芯一个码）。两种都支持。
- 使用人签收时扫实物上的仓储条码，RMLM 调「查询条码」核对后把码绑定到领用行：**一个码只挂一条领用行**；一张领料单行出了几个码，就生成几条领用行。
- 研发现场拆分物料时，RMLM 调「拆分申请新码」，由仓储系统发新码；RMLM 打印标签（二维码内容即条码原文），使用人贴到实物上。
- 退库的实物回到仓库后，由仓储系统自己扫码入库，RMLM 不推送。

| 码状态（RMLM 视角） | 谁负责 |
|---|---|
| B1 已赋码（在库） | 仓储系统 |
| B2 已领用 → B3 部分使用 → B5 已用完 / B4 已拆分替换 / B6 已退库 / B7 已报废 | RMLM |

## 二、通用约定

| 项 | 约定 |
|---|---|
| 协议 | HTTPS（内网可用 HTTP），JSON，UTF-8 |
| 地址 | 基础地址由仓储系统提供，填进 RMLM 的 `WMS_BASE_URL`，例如 `http://wms.internal/api`；下文路径都接在它后面 |
| 鉴权 | 请求头 `Authorization: Bearer <令牌>`。令牌由仓储系统发给 RMLM，填进 `WMS_TOKEN`，只放服务器 `.env` |
| 返回格式 | HTTP 200，`{"code": 0, "message": "ok", "data": {...}}`。`code ≠ 0` 为业务错误，`message` 会原样显示给使用人，请写成中文、说清楚原因 |
| 条码不存在 | `code = 404` |
| 超时 | RMLM 默认等 10 秒（`WMS_TIMEOUT`）。超时或 5xx 时 RMLM 提示"仓储系统暂时连不上，请稍后重试"，本次签收 / 拆分不生效 |
| 数量 | 十进制数，最多 3 位小数，单位与金蝶物料单位一致 |

## 三、接口 1：查询条码

`GET /rmlm/v1/barcodes/{barcode}`

签收时，使用人每扫一个码调一次；扫码页扫到中台还没有的条码时也会调用，用来找到对应的待签收行。

**返回 data：**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `barcode` | string | 是 | 条码原文 |
| `material_code` | string | 是 | 金蝶物料编码，须与金蝶一致 |
| `qty` | number | 是 | 该码对应的数量（一件一码时为这一件的数量，如 100 米；一批一码时为这一批的数量，如 50 个） |
| `unit` | string | 否 | 单位 |
| `kind` | string | 否 | `PIECE` 一件一码 / `BATCH` 一批一码，仅作显示 |
| `status` | string | 是 | `IN_STOCK` 在库 / `OUTBOUND` 已出库 / `SPLIT` 已拆分作废 / `SCRAPPED` 已报废 / `VOID` 作废 |
| `out_doc_no` | string | 否 | 出库时对应的金蝶单号（如 `QTCK-ADT-26100178`）。**强烈建议提供**，RMLM 用它核对"扫的码是不是这张单出的" |
| `out_line_no` | int | 否 | 出库对应的金蝶单据行号 |
| `parent_barcode` | string | 否 | 由哪个码拆出来的 |

**示例：**

```json
{"code": 0, "message": "ok", "data": {
  "barcode": "WMS2611000123", "material_code": "1000454", "qty": 100, "unit": "米",
  "kind": "PIECE", "status": "OUTBOUND", "out_doc_no": "QTCK-ADT-26100178", "out_line_no": 1
}}
```

**RMLM 签收时的校验**（任一不满足，签收不生效）：

1. 条码存在，`status = OUTBOUND`。在库的码提示"请先在仓储系统做出库"；
2. `material_code` 与领用行物料一致；
3. 有 `out_doc_no` 时，须等于领用行绑定的金蝶单号（紧急领用还没开单的行不校验这一项）；
4. 该码在 RMLM 里没有被其他领用行用过；
5. 本次扫到的所有码数量合计 = 领用行数量。一批一码而只领了其中一部分的，请仓库在出库时先在仓储系统里拆码、按实发数量贴新标签。

## 四、接口 2：拆分申请新码

`POST /rmlm/v1/barcodes/split`

研发现场把一件料分给多个项目或多个人时调用。拆分规则：拆出合计 + 余量 + 损耗 = 原码当前结存；原码提交后立即失效；**余量也要换新码**。

**请求：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `request_id` | string | 幂等键。同一个 `request_id` 重复请求，必须返回第一次发的那批码，不能重复发码 |
| `parent_barcode` | string | 被拆的原码 |
| `material_code` | string | 物料编码 |
| `pieces` | number[] | 每一份的数量，每份发一个新码。**余量排在最后一份** |
| `operator` | string | 操作人姓名（留痕用） |
| `project_code` | string | 项目号（留痕用） |

```json
{"request_id": "RMLM-WMS2611000123-1a2b3c4d", "parent_barcode": "WMS2611000123", "material_code": "1000454",
 "pieces": [40, 25, 30], "operator": "张三", "project_code": "PDJ20251101"}
```

**返回 data：** `barcodes` 数组，**顺序与 `pieces` 一一对应**。

```json
{"code": 0, "message": "ok", "data": {"barcodes": [
  {"barcode": "WMS2611000201", "qty": 40},
  {"barcode": "WMS2611000202", "qty": 25},
  {"barcode": "WMS2611000203", "qty": 30}
]}}
```

**仓储系统需要做的：**

- 新码的 `status` 为 `OUTBOUND`，`parent_barcode` 指向原码，物料与原码相同；
- 原码置为 `SPLIT`，以后再查询返回 `SPLIT`；
- **不要**用"新码合计 = 原码出库数量"去拦截：研发现场在拆分前可能已经用掉一部分、拆分时还可能有损耗，数量守恒由 RMLM 校验；
- 原码已被另一个 `request_id` 拆过时，返回 `code ≠ 0` 并说明"该码已拆分"。

## 五、RMLM 侧配置

在 RMLM 服务器 `.env` 里填写：

```
WMS_BASE_URL=http://仓储系统地址/api
WMS_TOKEN=仓储系统发给 RMLM 的令牌
WMS_TIMEOUT=10
```

两项都填才启用。**未配置时**，RMLM 自己发 RM 开头的临时码（仅供开发、测试、演示），签收不需要扫码。

## 六、联调清单

1. 仓储系统提供测试环境地址和令牌；
2. 准备一张金蝶领料单：一行一件一码（如 2 卷光缆、2 个码）、一行一批一码（如 1 袋插芯、1 个码）；
3. 在 RMLM 走一遍：申请 → 审核 → 金蝶开单过账 → 使用人扫码签收（第一行应生成 2 条领用行）；
4. 拆分其中一卷光缆，确认仓储系统里新码可查、原码变为 `SPLIT`；
5. 异常：扫在库码、扫别的单的码、扫物料不符的码、扫同一个码两次、断网，都应给出明确提示。
