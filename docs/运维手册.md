## 一、系统概览

### 1. 组成

```
浏览器（电脑 / 企微 H5 /m / PDA）
        │ HTTPS（企业已备案域名，RMLM_PUBLIC_URL）
  nginx（HTTPS、静态页面、/api 转发）          ← 本机或 DMZ
        │ http://127.0.0.1:8000
  uvicorn + FastAPI（backend/app）            ← systemd 服务 rmlm
   ├─ 进程内定时任务（每 15 分钟一次巡检，不依赖 Redis）
   ├─ 照片目录（RMLM_PHOTO_DIR，永久保存）
   └─ MySQL 8（库 rmlm，utf8mb4）
        │
  外部系统（都可选，不配就降级）：
   金蝶云星空 WebAPI（只读） / 企业微信 qyapi.weixin.qq.com / 仓储系统 WMS
```

- **一个后端进程即可**：页面（`frontend/dist`）、接口（`/api/*`）、健康检查（`/health/*`）都由同一个 uvicorn 提供；nginx 只负责 HTTPS 和转发。
- **没有 Redis、没有消息队列**：定时任务跑在后端进程里的一个线程中，多进程 / 多实例时靠 MySQL 命名锁 `rmlm_tick` 保证同一时刻只有一个在跑。
- **表结构自动维护**：每次启动自动建缺少的表、补新增的列和索引、把定义里改长了的字符串列加长。**不删列、不改其他类型**，没有单独的迁移脚本。

### 2. 数据在哪里

| 数据 | 位置 | 是否必须备份 |
|---|---|---|
| 业务数据（台账、单据、待办、审计日志、定时任务水位、系统设置） | MySQL 库 `DB_NAME`（默认 `rmlm`） | **必须** |
| 现场照片（压缩到约 300KB、带水印，永久保存，不能删除） | `RMLM_PHOTO_DIR`（未设置时为 `backend/data/photos`），按 `年/月/随机名.jpg` 存放 | **必须** |
| 配置与密钥 | 仓库根目录 `.env`（不进仓库） | **必须**（单独、加密保存） |
| 程序 | git 仓库目录 | 不用，可随时重新拉取 |
| 前端构建产物 | `frontend/dist` | 不用，可重新构建 |
| Python 虚拟环境 | `backend/.venv` | 不用，可重建 |

### 3. 端口

| 端口 | 谁监听 | 对谁开放 |
|---|---|---|
| 443（及 80 跳转） | nginx | 用户、企微客户端（经 DMZ） |
| 8000 | uvicorn | **只对本机**（`--host 127.0.0.1`），不对外 |
| 3306 | MySQL | 只对应用服务器 |

## 二、环境要求

### 1. 服务器

| 项 | 建议 |
|---|---|
| 操作系统 | Linux x86_64（Debian 12 / Ubuntu 24.04 / 麒麟 / 统信等均可）。下文命令以 Debian / Ubuntu 为例 |
| 规格 | 2 核 4G 起步，研发部门规模够用；磁盘按照片估算：每张约 300KB，1 万张约 3GB，预留 3 年增长 |
| 时区 | **必须是 Asia/Shanghai**：系统按服务器本地时间存储、计算时限（4 小时提醒、24 小时升级、每日 / 每月任务） |
| Python | **3.11 及以上**（推荐 3.13，与 Docker 镜像一致）。Ubuntu 22.04 自带 3.10，需另装 |
| Node.js | 18 及以上，**只在构建前端时需要**；也可以在别的机器构建好 `frontend/dist` 再拷过来 |
| 中文字体 | 照片水印里有人名，要有中文字体，否则显示成方块。Debian / Ubuntu 装 `fonts-wqy-zenhei`；其他系统用 `RMLM_WATERMARK_FONT` 指定字体文件 |
| nginx | 任一稳定版，需要 `ngx_http_realip_module`（发行版自带的一般都有） |

### 2. MySQL

- **MySQL 8**，字符集 **utf8mb4**。推荐用公司已有的 MySQL，纳入其统一备份。
- 应用账号需要库内全部权限（启动时会建表、加列、加索引、去掉多余的唯一索引）。
- 不需要改时区、`sql_mode` 等全局参数。

### 3. 网络

应用服务器要同时满足：

| 方向 | 目标 | 用途 |
|---|---|---|
| 出站 | 金蝶服务器 `K3_SERVER_URL`（内网） | 物料、单据只读同步 |
| 出站 | `https://qyapi.weixin.qq.com` | 企微登录、通讯录、消息推送 |
| 出站 | 仓储系统 `WMS_BASE_URL` | 查条码、拆分申请新码 |
| 出站（仅安装 / 升级时） | PyPI、npm 源（或国内镜像） | 装依赖 |
| 入站 | 经 DMZ 反向代理，用企业已备案的 HTTPS 域名 | 企微客户端、外网手机访问 |

企微后台还要登记：**网页授权可信域名** = `RMLM_PUBLIC_URL` 的域名；**企业可信 IP** = 应用服务器访问企微的**出口 IP**。

> 手机摄像头扫码、企微网页授权**都要求 HTTPS**，用 http 访问时这两项不可用。

## 三、首次部署（Linux）

下文约定：程序目录 `/opt/rmlm`，运行账号 `rmlm`，照片目录 `/data/rmlm/photos`，备份目录 `/backup/rmlm`。可按实际情况替换。

### 1. 准备 MySQL

在 MySQL 上执行（密码换成自己的强密码）：

```sql
CREATE DATABASE rmlm DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE USER 'rmlm'@'应用服务器IP' IDENTIFIED BY '强密码';
GRANT ALL PRIVILEGES ON rmlm.* TO 'rmlm'@'应用服务器IP';
FLUSH PRIVILEGES;
```

表不用手工建，首次启动时自动建。

### 2. 准备服务器

```bash
sudo timedatectl set-timezone Asia/Shanghai
```
```bash
sudo apt install -y git python3 python3-venv fonts-wqy-zenhei nginx rsync mysql-client
```
```bash
sudo useradd --system --create-home --home-dir /home/rmlm --shell /usr/sbin/nologin rmlm
```
```bash
sudo mkdir -p /opt/rmlm /data/rmlm/photos /backup/rmlm && sudo chown -R rmlm:rmlm /opt/rmlm /data/rmlm /backup/rmlm
```

确认 Python 版本 ≥ 3.11：

```bash
python3 --version
```

> Debian / Ubuntu 上 `mysql-client` 包名可能是 `default-mysql-client` 或 `mariadb-client`，只用于备份恢复，`mysqldump` 能连 MySQL 8 即可。

### 3. 获取代码

```bash
sudo -u rmlm git clone -b rmlm-v1 <仓库地址> /opt/rmlm
```

### 4. 配置 `.env`

```bash
cd /opt/rmlm && sudo -u rmlm cp .env.example .env && sudo chmod 600 .env
```

用编辑器打开 `/opt/rmlm/.env`，`.env.example` 里每项都有说明。上线至少改这些：

| 配置 | 怎么填 |
|---|---|
| `DB_HOST` `DB_PORT` `DB_NAME` `DB_USER` `DB_PASSWORD` | 第 1 步建好的库和账号 |
| `RMLM_JWT_SECRET` | 至少 16 位随机字符，用 `python3 -c "import secrets;print(secrets.token_urlsafe(32))"` 生成。为空、示例值或过短时**拒绝启动** |
| `RMLM_ADMIN_USER` / `RMLM_ADMIN_PASSWORD` | 首次启动时创建的管理员。**只在库里还没有任何账号时生效**，之后改这两项没有作用 |
| `RMLM_PHOTO_DIR` | `/data/rmlm/photos`（放到程序目录之外，便于备份和升级） |
| `RMLM_PUBLIC_URL` | 对外 HTTPS 地址，如 `https://rmlm.example.com`（启用企微时必填） |
| `K3_*` / `WECOM_*` / `WMS_*` | 按需填写，见第七节；不填就自动降级 |

`.env` 的书写规则（同时适用于 `start.py` 和 systemd）：

- 一行一项 `名称=值`，`#` 开头是注释；**值后面不要写注释**。
- 值里有空格、`$`、`\`、引号时，用**单引号**整个包住，如 `DB_PASSWORD='a$b\c'`。
- `.env` 里的 `RMLM_HOST`、`RMLM_PORT` 只给 `start.py` 用；按本手册用 systemd 运行时，监听地址和端口写在服务文件里。
- 第五部分【Docker 部署】的配置项不用管。

### 5. 安装后端依赖、构建前端

```bash
cd /opt/rmlm && sudo -u rmlm python3 -m venv backend/.venv
```
```bash
sudo -u rmlm backend/.venv/bin/pip install -q --upgrade pip && sudo -u rmlm backend/.venv/bin/pip install -q -r backend/requirements.txt
```

国内服务器下载慢时加镜像，如 `-i https://mirrors.aliyun.com/pypi/simple`。

构建前端（需要 Node.js 18+；装依赖用 `npm ci`，严格按 `package-lock.json`）：

```bash
cd /opt/rmlm/frontend && sudo -u rmlm npm ci --no-audit --no-fund && sudo -u rmlm npm run build
```

国内慢时加 `--registry=https://registry.npmmirror.com`。构建完成后应有 `frontend/dist/index.html`。

> 服务器上不想装 Node.js：在任一台装了 Node.js 的机器上，对**同一个提交**执行上面的构建，把 `frontend/dist` 整个目录拷到服务器的 `/opt/rmlm/frontend/dist`。

### 6. 首次试运行

用仓库自带的 `start.py` 试跑一次：它会检查数据库能否连上、端口是否被占用，有问题给中文提示。

```bash
cd /opt/rmlm && sudo -u rmlm python3 start.py
```

看到 `启动完成后浏览器打开 http://localhost:8000` 且没有报错后，在服务器上另开一个终端检查：

```bash
curl -s http://127.0.0.1:8000/health/ready
```

返回 `{"status":"UP","db":"UP"}` 即正常（首次启动已自动建表、建管理员）。然后在试运行的终端按 **Ctrl+C** 停止，改用下一步的 systemd 服务长期运行。

### 7. 注册 systemd 服务

新建 `/etc/systemd/system/rmlm.service`：

```ini
[Unit]
Description=RMLM 研发物料管家
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=rmlm
Group=rmlm
WorkingDirectory=/opt/rmlm/backend
EnvironmentFile=/opt/rmlm/.env
Environment=TZ=Asia/Shanghai PYTHONUNBUFFERED=1 PYTHONIOENCODING=utf-8
# 只监听本机，由 nginx 对外。--workers 一般为 1；要加时不超过 CPU 核数、不超过 4（定时任务有命名锁，不会重复执行）
ExecStart=/opt/rmlm/backend/.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1 --proxy-headers --timeout-graceful-shutdown 10
# 停止时最多等 10 秒让进行中的请求结束；后台还有线程（如手动金蝶同步）时程序 5 秒后自行退出
TimeoutStopSec=30
# 数据库没起来、启动失败时 10 秒后重试
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
```

MySQL 和应用在同一台机器时，把 `After=` 改成 `After=network-online.target mysql.service`。

```bash
sudo systemctl daemon-reload && sudo systemctl enable --now rmlm
```
```bash
systemctl status rmlm --no-pager && curl -s http://127.0.0.1:8000/health/ready
```

> - nginx 和应用不在同一台机器时：`--host` 改成本机内网 IP，并加 `--forwarded-allow-ips <nginx 的 IP>`，否则审计日志里的来源地址都是 nginx 的地址；防火墙只放行 nginx 访问 8000。
> - 也可以让 systemd 直接运行 `python3 /opt/rmlm/start.py`（`WorkingDirectory=/opt/rmlm`，不写 `EnvironmentFile`）：更省事，但只能单进程，且升级后首次启动时会联网装依赖。正式环境推荐上面的写法。

### 8. 配置 nginx（HTTPS 反向代理）

下面的配置照搬仓库里 Docker 版的 `frontend/nginx.conf`，只改了页面目录和转发地址。新建 `/etc/nginx/conf.d/rmlm.conf`，域名和证书换成自己的：

```nginx
# 外层还有 HTTPS 反向代理（DMZ）时沿用它传来的协议；直接访问时用本层的
map $http_x_forwarded_proto $rmlm_fwd_proto {
    default $http_x_forwarded_proto;
    ""      $scheme;
}

server {
    listen 80;
    server_name rmlm.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name rmlm.example.com;
    ssl_certificate     /etc/nginx/ssl/rmlm.example.com.crt;
    ssl_certificate_key /etc/nginx/ssl/rmlm.example.com.key;

    root /opt/rmlm/frontend/dist;
    gzip on;
    gzip_types text/plain application/javascript application/json text/css image/svg+xml;
    # 照片上传（原图最大 15MB）、Excel 导入。nginx 默认只有 1MB，不改会报 413
    client_max_body_size 50m;

    # 来源地址（审计日志用）：只信任内网反向代理传来的 X-Forwarded-For
    set_real_ip_from 10.0.0.0/8;
    set_real_ip_from 172.16.0.0/12;
    set_real_ip_from 192.168.0.0/16;
    set_real_ip_from 127.0.0.1;
    real_ip_header X-Forwarded-For;
    real_ip_recursive on;

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $rmlm_fwd_proto;
        # 金蝶全量同步、企微通讯录同步、大批量导入耗时较长
        proxy_read_timeout 600s;
        proxy_send_timeout 600s;
    }

    location /health/ {
        proxy_pass http://127.0.0.1:8000;
    }

    # index.html 每次向服务器确认：升级后浏览器立即拿到新页面
    location = /index.html {
        add_header Cache-Control "no-cache";
    }

    # 构建产物文件名带哈希，可长期缓存
    location /assets/ {
        add_header Cache-Control "public, max-age=31536000, immutable";
        try_files $uri =404;
    }

    # 前端路由（/ledger、/m/scan 等）都回到 index.html
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

nginx 进程要能读 `/opt/rmlm/frontend/dist`（默认目录权限 755 即可）。

```bash
sudo nginx -t && sudo systemctl reload nginx
```

> 由 DMZ 的代理终结 HTTPS、再用 http 转到本机时：本机 nginx 只留 `listen 80;` 那个 server（去掉 301 跳转，把 443 server 的内容挪进去），DMZ 代理同样要设 `client_max_body_size 50m` 和 600 秒读超时，并传 `X-Forwarded-For`、`X-Forwarded-Proto`。

### 9. 上线前初始化

1. 用 `.env` 里的管理员账号登录，**点左侧栏左下角的当前账号 →「修改密码」，改掉初始密码**（系统不强制改）。
2. 系统管理 → 用户管理：建号、勾选角色、设置直属上级（可 Excel 批量导入）；启用企微时点「同步企微通讯录」。
3. 基础数据 → 基础资料：导入项目、物料（含单价）、库位和报废箱；启用金蝶时在「物料」点「从金蝶同步 → 全量」。
4. 启用金蝶时：仓库作业 → ERP 单据，点「从金蝶同步领料单」做首次同步，确认「自动同步设置」为开启、能看到最近同步时间。
5. 配置定时备份（第九节）。
6. 浏览器、手机企微各走一遍：登录 → 提交申请 → 审核 → 签收，确认推送能收到、手机能调起摄像头。

### 10. Windows 服务器（不推荐）

`start.py` 在 Windows 上同样可用（`python start.py`）。要开机自启，可用 NSSM 等工具把 `python start.py`（起始目录 = 仓库根目录）注册为服务，或在「任务计划程序」里设为「系统启动时运行」。停止后确认 8000 端口已释放再启动。HTTPS 仍需前置反向代理。以下各节以 Linux 为准，命令需自行换成 Windows 写法。

## 四、日常启停与状态查看

| 操作 | 命令 |
|---|---|
| 启动 / 停止 / 重启 | `sudo systemctl start rmlm` / `stop rmlm` / `restart rmlm` |
| 状态 | `systemctl status rmlm --no-pager` |
| 健康检查（进程活着） | `curl -s http://127.0.0.1:8000/health/live` → `{"status":"UP"}` |
| 健康检查（能连上数据库） | `curl -s http://127.0.0.1:8000/health/ready` → `{"status":"UP","db":"UP"}`；数据库不通时返回 **503** |
| 看实时日志 | `journalctl -u rmlm -f` |
| 看今天的错误 | `journalctl -u rmlm --since today -p warning` |
| 看外部接口是否启用 | `curl -s http://127.0.0.1:8000/api/auth/config` → `{"wecom":true/false,"wms":true/false}` |

**关于日志**：

- uvicorn 的启动信息、访问日志（每个请求一行）和程序的**警告、错误（含异常堆栈）**都写到 systemd 日志（journald），时间戳由 journald 加。
- 程序自己的普通信息（如"定时任务执行结果""表结构已补列"）**不输出到日志**。定时任务是否执行、结果如何，看第八节的页面和 `job_run` 表。
- journald 默认有容量上限，要长期留存访问日志时在 `/etc/systemd/journald.conf` 设置 `SystemMaxUse=`。

**停服务的影响**：停止时最多等 10 秒让进行中的请求结束；正在跑的定时任务不等，未提交的事务由 MySQL 回滚，下一次巡检会重新处理，不会丢数据或重复记账。

## 五、配置管理

所有配置都在 `/opt/rmlm/.env`，**改完重启服务才生效**：

```bash
sudo systemctl restart rmlm
```

| 改了什么 | 还要做什么 |
|---|---|
| 数据库连接 `DB_*` | 重启后看 `/health/ready` |
| `RMLM_JWT_SECRET` | 所有人的登录立即失效，需重新登录（在企微里打开时会自动重新授权登录） |
| `RMLM_JWT_HOURS`（登录有效期，默认 12 小时） | 只影响之后新登录的 |
| `RMLM_PHOTO_DIR` | **先把旧目录的照片整体搬到新目录**（保持 `年/月/文件名` 结构），否则历史照片打不开 |
| `K3_LL_BILL_TYPES`（研发领料的单据类型） | 重启后做一次**全量同步**：ERP 单据 →「从金蝶同步领料单」旁的下拉 →「全量同步」（或附录 A 的 `POST /api/erp/docs/sync?full=true`），把新类型的历史单据补拉进来 |
| `K3_SYNC_START_DATE` / `K3_SYNC_START_MONTHS` | 只影响首次同步和手动全量同步的起点，平时增量不受影响 |
| `K3_USE_ORG` | 先和业务确认；改后做一次物料全量同步和单据全量同步 |
| 企微 `WECOM_*` / `RMLM_PUBLIC_URL` | 三项（企业 ID、AgentId、Secret）要么都填、要么都空；改域名时同步改企微后台的可信域名、应用主页 |
| `WMS_BASE_URL` / `WMS_TOKEN` | **启用后签收必须扫仓储条码**；上线中途开关会混用两种码，须业务确认 |
| `RMLM_SCHEDULER` | 正式环境必须为 `1`，见第六节 |
| `RMLM_OVER_ISSUE_PCT` | 业务参数，按业务要求改 |

网页上也有一项设置，存在数据库里、**不用重启**：仓库作业 → ERP 单据 →「自动同步设置」（管理员）：金蝶领料单自动同步的开关和间隔（15 分钟～24 小时）。

> 改 `.env` 前先复制一份：`cp .env .env.bak.$(date +%F)`，出问题可以马上换回来。`.env` 含密钥，备份副本同样 `chmod 600`。

## 六、定时任务

### 1. 运行方式

- 后端进程启动后 **15 分钟**执行第一次巡检，之后每次巡检结束后再等 15 分钟（不会叠着跑）。
- 每次巡检先做"每 15 分钟"的事，再按日期判断要不要做每日、每周、每季、每月的事。每日的事在**每天第一次巡检时**做（约 0:00–0:15；当天服务刚重启过则在启动 15 分钟后）。
- 每一步单独回滚：某一步出错只影响这一步，并给所有管理员派「定时任务出错」待办，其余步骤照常。
- 多进程 / 多实例时，靠 MySQL 命名锁 `rmlm_tick` 保证只有一个在跑，拿不到锁的直接跳过。
- `.env` 的 `RMLM_SCHEDULER=0` 会关掉定时任务：**正式环境必须为 1**，否则金蝶单据不拉、提醒升级都不发生。只在测试库、临时排查用的第二个实例上设 0。

> 服务如果**反复重启、每次运行不到 15 分钟**，定时任务永远轮不到执行。

### 2. 时间表

| 周期 | 内容 |
|---|---|
| 每 15 分钟 | 企微推送补发；拉取金蝶领料单（按网页设置的间隔，默认每次都拉）并按申请号自动生成领用行；审核提醒（4 小时）与升级上一级（24 小时）；紧急领用 24 小时未补齐检查；ERP 有单无明细（24 小时）；关闭已办完的待办；待办升级（48 小时 → 直属上级，3 天 → 研发副总）；结存异常锁行 |
| 每天 | 每日对账；金蝶物料增量同步；企微通讯录同步（人员、职务、直属上级、离职）；D02 实验结论 30 天预警；超期待办与冻结、长周期到期提醒、项目结项清零检查；长周期季度确认过期处理 |
| 每周（周一） | 生成报废批次 |
| 每季（季度第一天） | 发起长周期物料季度在用确认（7 天内完成）；记录季初超期快照 |
| 每月（1 日） | 给财务派关账提醒：3 日前完成上月中台关账 |

服务在零点前后停机：恢复后第一次巡检会补做当天的每日任务；每周、每季、每月同理（在该周期内第一次巡检时做）。

### 3. 怎么看执行情况

执行记录在 `job_run` 表（SQL 见附录 B）：

| name | 含义 | last_key |
|---|---|---|
| `daily` / `weekly` / `quarterly` / `monthly` | 每日 / 每周 / 每季 / 每月任务 | 最近执行的周期，如 `2026-11-27`、`2026-W48`、`2026-Q4`、`2026-11` |
| `k3_docs` | 金蝶单据同步 | 增量水位（金蝶修改时间），`last_result` 是最近一次结果 |
| `k3_material` | 金蝶物料同步 | 同上 |
| `wecom_contacts` | 企微通讯录同步 | — |

判断正常：`daily.last_key` 是今天（0:15 以后）；启用金蝶时 `k3_docs.last_run_at` 距现在不超过设置的间隔 + 15 分钟。

### 4. 手动触发

一般不需要。排除故障后想立即验证，管理员可以调接口（方法见附录 A）：

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8000/api/admin/jobs/tick
```

- `tick` = 完整走一遍巡检，每日 / 每周等任务**仍按周期判断**（今天已做过就不再做），**推荐只用它**。
- `quarter_hour` / `daily` / `weekly` / `quarterly` / `monthly` 会**强制**执行对应任务，不看是否已做过，也不拿命名锁，可能和后台巡检同时跑。除非明确需要（如补发漏掉的季度确认），不要用。

## 七、外部接口运维：金蝶 / 企业微信 / 仓储

三个对接都可选。启用条件：金蝶 `K3_SERVER_URL` `K3_ACCT_ID` `K3_USERNAME` `K3_APP_ID` `K3_APP_SECRET` 五项都填；企微 `WECOM_CORP_ID` `WECOM_AGENT_ID` `WECOM_SECRET` 三项都填；仓储 `WMS_BASE_URL` `WMS_TOKEN` 两项都填。

### 1. 金蝶云星空（只读，不回写金蝶）

**同步什么**

| 内容 | 方式 |
|---|---|
| 物料档案 | 每天增量；手动：基础数据 → 基础资料 → 物料 →「从金蝶同步」（增量）/「全量」 |
| 研发领料单（其他出库单中 `K3_LL_BILL_TYPES` 类型） | 按网页设置的间隔增量拉取（默认 15 分钟）；手动：仓库作业 → ERP 单据 →「从金蝶同步领料单」（增量），旁边下拉里是「全量同步」 |
| 退料单、报废单 | 不批量拉，领料专员分摊 / 核销时输入金蝶单号按单取回 |

**增量机制**：水位记在 `job_run`（`k3_docs`、`k3_material`）的 `last_key`，每次从水位往前回退 10 分钟再拉，避免漏单；按单据号对齐，重复拉取不会重复入库。首次同步和「全量」只拉 `K3_SYNC_START_DATE`（不填为今天往前 `K3_SYNC_START_MONTHS` 个月，默认 3 个月）之后修改过的单据。

**查看状态**：ERP 单据页顶部显示是否已配置、最近同步时间、结果、下次自动同步时间；接口 `GET /api/erp/docs/sync/status`。

**常见问题**

| 现象 | 处理 |
|---|---|
| 「金蝶登录失败」 | 核对账套 ID、用户名、AppID、AppSecret；金蝶第三方应用是否被禁用或过期 |
| 「连接金蝶失败」「金蝶服务异常」 | 服务器到金蝶内网不通或金蝶服务异常。分页查询会按 `K3_PAGE_RETRIES`（默认 3 次）、间隔 `K3_PAGE_RETRY_SECONDS`（10 秒）自动重试 |
| 查询超时 | 单据多时调大 `K3_QUERY_TIMEOUT`（默认 120 秒）；首次同步范围太大时缩短 `K3_SYNC_START_MONTHS` |
| 「金蝶查询 … 失败：…（权限）」 | 金蝶应用账号缺少对应单据 / 基础资料的查看权限 |
| 「金蝶单据同步跳过 XXX：…已关账…」 | 金蝶里改了**已关账月份**的单据，中台不跟着改。由财务开调整单处理 |
| 「金蝶单据同步跳过 XXX：…物料编码不存在」 | 先同步物料（增量即可），再手动同步单据 |
| 「金蝶单据 XXX 已反审核或作废」待办（给领料专员） | 业务核对已签收 / 已分摊的明细；对账会把差额列进差异 |
| 单据拉到了但没生成领用行 | 备注里没写申请号、申请未审核通过、同一物料有多条明细时对不上，由领料专员在「出库开单」按绑定建议手工绑定。属业务处理 |
| 接口长时间不可用 | 可在 ERP 单据页手工录入 / Excel 导入应急；恢复后增量同步会按单号对齐，不会重复 |

**重拉一段历史**：设置 `K3_SYNC_START_DATE=YYYY-MM-DD`，重启后在 ERP 单据页做「全量同步」；做完把该项清空并重启。

### 2. 企业微信

**功能**：企微内打开免密登录；待办同步推送企微消息（点开直达）；每天同步通讯录。三项配置是一个总开关，填齐后三个功能同时开启。

**企微后台要配好**：应用主页 `{RMLM_PUBLIC_URL}/`；网页授权可信域名；企业可信 IP（服务器出口 IP）；应用可见范围（研发部门）。通讯录同步可用单独的「通讯录同步 Secret」（`WECOM_CONTACT_SECRET`，只读），不填时用应用 Secret（需应用有通讯录读取权限）。

**查看状态**：系统管理 → 用户管理，列表下方显示企微通讯录最近同步时间；接口 `GET /api/admin/wecom/status`。

**推送机制**：待办生成、事务提交后立即推送；失败的每 15 分钟补发一次，**累计失败 3 次后放弃**（`todo.push_state = 'FAIL'`），站内待办不受影响。排除原因后可重新排队补发（附录 B）。

**通讯录同步规则**：按企微 UserID 对齐；中台已有同名、未绑定企微的账号（Excel 导入的）自动绑定；新人自动开号（只有使用人角色）；姓名、职务、直属上级以企微为准；企微里离职 / 停用 / 移出同步范围的人，**名下没有结存直接停用，有结存的不停用**，给直属上级派「离职清零」待办，清完后下次同步再停用。角色只在本系统勾选。

**常见问题**

| 现象 | 处理 |
|---|---|
| 「企业微信账号 xxx 尚未开通研发物料管家」 | 此人还没同步进来：用户管理 →「同步企微通讯录」，或手工建号并填企微 UserID |
| 「不是本企业成员，无法登录」 | 用个人微信或其他企业的企微打开了 |
| 企微里打开提示回调域名不对 / 登录后跳到错误地址 | `RMLM_PUBLIC_URL` 和企微后台可信域名不一致，或没填 `RMLM_PUBLIC_URL` |
| 企微接口报 IP 不在白名单（如错误码 60020） | 把服务器出口 IP 加到企微后台「企业可信 IP」 |
| 消息卡片点开打不开 | `RMLM_PUBLIC_URL` 没填或外网访问不到 |
| 「企业微信通讯录同步失败」待办 | 看待办里的错误；常见是 Secret 错、没有通讯录读取权限、`WECOM_ROOT_DEPT` 不存在 |

更换 Secret：改 `.env` 后重启；旧的 access_token 自动失效重取。

### 3. 仓储系统（WMS）

一期不对接时两项留空，系统自己发 RM 行码。启用后：签收必须扫仓储条码，拆分时向仓储申请新码。接口规范见 [仓储接口规范](仓储接口规范.md)。

| 现象 | 处理 |
|---|---|
| 「仓储系统暂时连不上，请稍后重试」 | 服务器到 `WMS_BASE_URL` 网络、仓储服务状态；仓储响应慢时调大 `WMS_TIMEOUT`（默认 10 秒） |
| 「仓储系统返回格式不正确 / 条码信息不完整 / 新码数量不符」 | 仓储接口实现与规范不一致，带上时间和条码找仓储系统排查 |
| 4xx 业务错误（条码不存在等） | 原样提示给用户，属业务问题 |

## 八、监控与巡检

### 1. 健康检查（接入公司监控）

| 地址 | 用途 | 异常时 |
|---|---|---|
| `GET /health/live` | 进程活着 | 无响应 → 服务挂了，看 `journalctl -u rmlm` |
| `GET /health/ready` | 能连上数据库 | 503 → 数据库不通 |
| `GET /api/health` | 经 nginx 的整条链路 | 从外部访问 `https://域名/api/health` 应返回 `{"ok":true}` |

建议监控每分钟探测 `https://域名/api/health` 和本机 `/health/ready`，连续 3 次失败告警。同时监控磁盘（照片目录、备份目录、MySQL 数据目录）使用率，超过 80% 告警。

### 2. 管理员待办（系统自己发出的告警）

以下待办派给**系统管理员**账号，显示在「我的待办」和「用户管理」菜单的数字上。管理员账号要有真人负责，并绑定企微以便收到推送。

| 待办 | 含义 | 处理 |
|---|---|---|
| 定时任务出错 | 某一步定时任务抛错，标题里有步骤名和错误 | 看 `journalctl -u rmlm` 里对应时间的堆栈，排除后用 `tick` 验证（第六节） |
| 同步失败 | 金蝶物料 / 单据同步、企微通讯录同步失败，或某张金蝶单据被跳过 | 按第七节处理 |
| 锁行修正 | 某领用行结存异常（为负或超过领用数量）已自动锁定，48 小时内修正 | 复盘该行流水，通过「冲销」修正；冲销复核通过、结存恢复正常后自动解锁 |
| 冲销复核 | 有人发起冲销，需 IT 复核，24 小时内处理（发起人和复核人不能是同一人） | 对账与报表 → 对账与关账 →「冲销」页签 |
| 对账差异待关闭 | 领料专员已认领的差异，需财务或 IT 关闭（认领人不能关自己认领的） | 业务处理 |
| 离职清零 | 企微离职的人直属上级不明时派给管理员 | 督促清零 |

> **注意：「定时任务出错」「同步失败」这两类待办不会自动关闭，界面上也关不掉**（系统规则是待办做完对应操作后自动关闭，而这两类没有对应的关闭动作）。同一问题只派一条（不重复派），**但原因排除后它仍挂着，48 小时后升级给管理员的直属上级，3 天后通知研发副总**，而且这期间同类新故障不会再派新待办。排除原因后请按附录 B 手工关闭。

### 3. 巡检清单

**每天（10 分钟）**

- [ ] `/health/ready` 正常；`journalctl -u rmlm --since yesterday -p warning` 没有新的异常堆栈
- [ ] 管理员待办里没有新的「定时任务出错」「同步失败」「锁行修正」；「冲销复核」当天处理
- [ ] 启用金蝶时：ERP 单据页「最近同步时间」在设定间隔内
- [ ] 昨晚备份成功（看备份日志和文件大小）

**每周**

- [ ] `job_run` 里 `daily` 每天都执行了、`weekly` 是本周（附录 B）
- [ ] 企微推送失败数（`push_state='FAIL'`）没有异常增长
- [ ] 磁盘：照片目录、备份目录、MySQL 增长正常
- [ ] 审计日志（系统管理 → 审计日志）抽看有无异常的大量失败请求（状态 401 / 403 / 500）

**每月**

- [ ] 1 日：确认 `monthly` 已执行、财务收到关账提醒；**3 日前**把待复核的冲销处理完（有待复核的冲销时，财务不能关账）
- [ ] 系统、MySQL、nginx 安全补丁（在低峰期，按第十节流程重启）

**每季度**

- [ ] 季度第一天确认 `quarterly` 已执行（使用人收到长周期季度确认待办）
- [ ] 做一次**恢复演练**（第九节第 4 点）

## 九、备份与恢复

照片和数据库**都要备份**，且要放到另一台机器或存储上。公司 MySQL 已统一备份时，可以只备份照片，但要确认其保留周期满足要求。

### 1. 备份账号配置

先建目录：

```bash
sudo mkdir -p /etc/rmlm
```

新建 `/etc/rmlm/backup.cnf`，避免密码出现在命令行和进程列表里：

```ini
[client]
host=MySQL地址
port=3306
user=rmlm
password=数据库密码
```

```bash
sudo chown rmlm:rmlm /etc/rmlm/backup.cnf && sudo chmod 600 /etc/rmlm/backup.cnf
```

### 2. 备份脚本

新建 `/usr/local/bin/rmlm-backup.sh`（`chmod 755`）：

```bash
#!/usr/bin/env bash
# RMLM 每日备份（非 Docker）：数据库每天一份、保留 30 天；照片永久保存且不会删除，按增量同步到一份镜像
set -euo pipefail
ROOT=${BACKUP_DIR:-/backup/rmlm}
PHOTO_DIR=${PHOTO_DIR:-/data/rmlm/photos}
DB_NAME=${DB_NAME:-rmlm}
DEST="$ROOT/$(date +%F)"
mkdir -p "$DEST" "$ROOT/photos"

if [ "${SKIP_DB:-0}" != "1" ]; then
  mysqldump --defaults-extra-file=/etc/rmlm/backup.cnf --single-transaction --no-tablespaces "$DB_NAME" \
    | gzip > "$DEST/rmlm.sql.gz"
fi
# 不加 --delete：照片只增不减，源目录误删时备份里还在
rsync -a "$PHOTO_DIR/" "$ROOT/photos/"
find "$ROOT" -maxdepth 1 -type d -name '20*' -mtime +30 -exec rm -rf {} +
echo "$(date '+%F %T') 备份完成：$DEST"
```

加到运行账号的定时任务（每天 2:30，避开 0:00 前后的每日任务）：

```bash
sudo -u rmlm crontab -e
```

```
30 2 * * * /usr/local/bin/rmlm-backup.sh >> /backup/rmlm/backup.log 2>&1
```

再用公司的备份系统把 `/backup/rmlm` 同步到异地；`.env` 单独加密保存一份。

### 3. 恢复

用于服务器损坏、误操作后回到某天的数据。

1. 停服务：

   ```bash
   sudo systemctl stop rmlm
   ```

2. 恢复数据库（恢复到**空库**或原库；dump 里每张表都是先删后建，原库中的数据会被覆盖）：

   ```bash
   gunzip -c /backup/rmlm/2026-11-27/rmlm.sql.gz | sudo -u rmlm mysql --defaults-extra-file=/etc/rmlm/backup.cnf rmlm
   ```

3. 恢复照片：

   ```bash
   sudo -u rmlm rsync -a /backup/rmlm/photos/ /data/rmlm/photos/
   ```

4. 程序：用备份当天对应的代码版本（见第十节「记录当前版本」）；`.env` 用备份的副本。
5. 启动并检查：

   ```bash
   sudo systemctl start rmlm && curl -s http://127.0.0.1:8000/health/ready
   ```

> 恢复后备份时间点之后的业务操作会丢失，需通知业务按纸面 / 金蝶记录补登。金蝶单据会在下一次同步时按水位自动补回。

### 4. 恢复演练（每季度）

在**测试机**上做（或在同一台机器另拉一份代码到别的目录、用单独的 `.env`），不要动正式库和正式照片目录：

1. 用 MySQL 管理员账号建测试库 `rmlm_restore` 并授权给一个测试账号（同第三节第 1 步）。
2. 导入最近一份备份：

   ```bash
   gunzip -c /backup/rmlm/2026-11-27/rmlm.sql.gz | mysql -h MySQL地址 -u 测试账号 -p rmlm_restore
   ```

3. 把备份里的照片拷一份给测试实例用（不要直接指向 `/backup/rmlm/photos`）。
4. 测试实例的 `.env`：`DB_NAME=rmlm_restore` 及测试账号；`RMLM_PHOTO_DIR` 指向第 3 步的照片副本；`RMLM_SCHEDULER=0`；同机演练时 `RMLM_PORT=8001`；**清空 `WECOM_*`、`K3_*`、`WMS_*`**——否则演练里产生的待办会推送到真人的企微。
5. `python3 start.py` 启动，登录抽查几条台账、照片能否打开。做完删掉测试库和照片副本。

## 十、升级与回退

### 1. 升级步骤

选低峰时段（避开 0:00–0:30 每日任务，避开每月 1–3 日关账期），提前通知用户，预计停机几分钟。

1. **备份**：

   ```bash
   sudo -u rmlm /usr/local/bin/rmlm-backup.sh
   ```

2. **记录当前版本**（回退用）：

   ```bash
   cd /opt/rmlm && sudo -u rmlm git rev-parse HEAD | sudo -u rmlm tee -a /backup/rmlm/versions.log
   ```

3. **拉取新代码**：

   ```bash
   sudo -u rmlm git pull --ff-only origin rmlm-v1
   ```

4. **看这次改了什么**（`旧版本` 换成第 2 步记录的提交号）：

   ```bash
   sudo -u rmlm git diff --stat 旧版本 HEAD -- backend/requirements.txt frontend/package-lock.json .env.example backend/app/models.py frontend/
   ```

   - `.env.example` 有变化：对照新增 / 改动的配置项，按需改 `.env`（新增项一般有默认值）。
   - `backend/app/models.py` 有变化：表结构有调整，启动时自动补列补索引；回退时要考虑恢复数据库（见下文）。

5. **更新后端依赖**（`requirements.txt` 有变化时）：

   ```bash
   sudo -u rmlm /opt/rmlm/backend/.venv/bin/pip install -q -r /opt/rmlm/backend/requirements.txt
   ```

6. **重新构建前端**（`frontend/` 有任何变化时；不确定就构建）：

   ```bash
   cd /opt/rmlm/frontend && sudo -u rmlm npm ci --no-audit --no-fund && sudo -u rmlm npm run build
   ```

7. **重启并检查**：

   ```bash
   sudo systemctl restart rmlm && sleep 5 && curl -s http://127.0.0.1:8000/health/ready
   ```
   ```bash
   journalctl -u rmlm --since "-5min" --no-pager
   ```

8. **冒烟测试**：浏览器强制刷新后登录、打开首页 / 领用台账 / ERP 单据；企微里打开一次；看 ERP 单据页同步状态正常。

> 前端构建期间页面可能短暂打不开（构建会清空 `dist` 再写入），所以第 6、7 步紧接着做。nginx 对 `index.html` 设了 `no-cache`，用户刷新即可拿到新页面。

### 2. 回退

1. 停服务，切回旧版本：

   ```bash
   sudo systemctl stop rmlm && cd /opt/rmlm && sudo -u rmlm git checkout 旧版本
   ```

2. 重新安装后端依赖、重新构建前端（同升级第 5、6 步）。
3. **数据库**：自动升级只会加列、加索引、加长字符串，不删数据。
   - 新版本没有改表结构（`models.py` 没变）：直接启动即可。
   - 改了表结构：旧程序遇到新加的、不允许为空的列时，新增数据可能报错。**稳妥做法是用升级前的备份恢复数据库**（第九节），代价是升级后的业务操作要补登。所以升级后先冒烟，确认问题尽早决定是否回退。
4. 启动并检查。问题修复后再回到分支最新：`sudo -u rmlm git checkout rmlm-v1 && sudo -u rmlm git pull --ff-only origin rmlm-v1`，按升级步骤重做。

## 十一、账号与安全

### 1. 账号

| 事项 | 做法 |
|---|---|
| 初始管理员 | 首次启动按 `.env` 的 `RMLM_ADMIN_USER` / `RMLM_ADMIN_PASSWORD` 创建，**之后改 `.env` 不起作用**。登录后立即改密码 |
| 新建 / 导入账号的初始密码 | 建号时不填密码、Excel 批量导入时，初始密码都是 `Rmlm@123456`。通知本人登录后修改；启用企微的人用企微登录，可不管密码 |
| 重置他人密码 | 用户管理 → 编辑 →「重置密码」填新密码。保存后此人**所有已登录设备立即失效** |
| 本人改密码 | 电脑版：左侧栏左下角的当前账号 →「修改密码」；手机版：首页「修改密码 / 退出」。至少 8 位；其他设备上的登录随即失效 |
| 停用账号（离职 / 调岗） | 用户管理 → 编辑 → 关掉「启用」开关。名下有结存、有待他确认的转交、有未开完单的申请时**不能停用**，先清零（界面会列出卡点） |
| 冻结 | 超期连续 2 周无动作时系统自动冻结新领用；**只能由直属上级在「我的团队」解冻**，管理员不能代解 |
| 角色 | 只在本系统勾选；企微同步不改角色 |

**管理员密码忘了、又没有其他管理员**：在服务器上生成新密码的哈希，直接改库：

```bash
/opt/rmlm/backend/.venv/bin/python -c "import bcrypt,getpass;print(bcrypt.hashpw(getpass.getpass('新密码：').encode(),bcrypt.gensalt(10)).decode())"
```

```sql
UPDATE users SET password_hash='上一步输出的整串', token_version=token_version+1, active=1 WHERE username='admin';
```

### 2. 安全要点

- `.env` 权限 `600`、属主 `rmlm`；**密钥只写在 `.env`**，不要提交到仓库、不要发到群里。
- uvicorn 只监听 `127.0.0.1`，8000 端口不对外；MySQL 3306 只对应用服务器开放。
- 系统**不做登录失败锁定**（业务确认），所以不要把登录页直接暴露到公网而不加防护；外网访问一律经 DMZ 反向代理，必要时在代理上做访问频率限制。
- 金蝶应用账号只给查看权限（物料、其他出库单、其他入库单等）；企微通讯录用只读 Secret。
- 怀疑令牌泄露时：更换 `RMLM_JWT_SECRET` 并重启，所有人需重新登录。
- 审计日志：所有 `/api/` 下的新增、修改、删除请求都记录（操作人、地址、状态码、来源 IP、请求内容；密码字段打码为 `***`），在系统管理 → 审计日志查看最近 500 条，更早的查 `audit_log` 表。

### 3. 数据增长与清理

系统**不会自动清理**任何数据：审计日志（`audit_log`，每个写请求一行）、待办（`todo`）、照片都会一直增长。照片按业务规则永久保存，**不能删**。审计日志如需归档，先和业务、审计确认保留期限，导出备份后再删旧数据。各表大小见附录 B。

## 十二、常见故障处理

| 现象 | 原因与处理 |
|---|---|
| 服务起不来，日志里有 `RMLM_JWT_SECRET 未设置、仍是示例值或少于 16 位` | 按第三节第 4 步生成并填入 |
| 服务起不来，日志里有数据库连接错误（`OperationalError` / `Access denied` / `Can't connect`） | 检查 MySQL 是否在运行、`DB_*` 是否正确、账号是否允许从本机连接、防火墙。可用 `sudo -u rmlm mysql --defaults-extra-file=/etc/rmlm/backup.cnf -e "select 1"` 验证 |
| `address already in use` / 端口被占用 | `sudo ss -lntp \| grep 8000` 找到占用进程；常见是手工用 `start.py` 起的没关 |
| 打开页面空白或 404 | 前端没构建或构建失败：确认有 `frontend/dist/index.html`，重新构建；nginx 的 `root` 是否指向 `frontend/dist` |
| 升级后页面空白、控制台报找不到 `assets/*.js` | 浏览器缓存了旧页面：强制刷新。检查 nginx 是否给 `index.html` 设了 `Cache-Control: no-cache` |
| 页面能开，所有接口 502 / 504 | 后端没在跑（`systemctl status rmlm`）；或耗时操作超过代理超时：本机 nginx 和 DMZ 代理都要设 600 秒 |
| 上传照片 / 导入 Excel 报 413 | nginx（及 DMZ 代理）`client_max_body_size` 太小，设 50m |
| 照片水印里的人名是方块 | 缺中文字体：`sudo apt install fonts-wqy-zenhei` 后重启，或用 `RMLM_WATERMARK_FONT` 指定字体文件 |
| 历史照片打不开（「系统内部错误」） | 照片目录改过或丢失：核对 `RMLM_PHOTO_DIR`，从备份恢复照片 |
| 手机扫码调不起摄像头 | 没用 HTTPS 访问 |
| 所有时限（提醒、升级、超期）都差 8 小时 | 服务器时区不对：`timedatectl` 应为 Asia/Shanghai，服务文件里有 `TZ=Asia/Shanghai`，改后重启 |
| 审核提醒、超期、金蝶单据都不动了 | 定时任务没跑：`RMLM_SCHEDULER` 是否为 1；服务是否在反复重启（`systemctl status` 看启动时间）；`job_run` 里 `daily` 是否停在某天；日志里有无「tick failed」 |
| 多实例时定时任务都不跑 | 有连接一直占着锁：`SELECT IS_USED_LOCK('rmlm_tick');` 返回占用的连接号，确认该连接的进程已挂死后在 MySQL 里 `KILL` 它 |
| 「定时任务出错」反复出现同一个错误 | 看日志里的堆栈；数据问题（如某行数据异常）带上待办标题找开发 |
| 企微、金蝶相关 | 见第七节 |
| 用户说收到「【二级】…同步失败」或副总收到「【三级挂账】…同步失败」 | 管理员没关掉已处理的「同步失败 / 定时任务出错」待办，按附录 B 关闭 |
| 财务关账提示「还有 N 笔待复核的冲销」 | IT 先在对账与关账 →「冲销」页签里复核完 |
| 财务关账提示「还有 N 条差额不为 0 的差异」 | 业务处理：领料专员认领、财务 / IT 按原因码关闭；差额必须为 0 |
| 已关账月份要更正 | 系统没有反关账功能，也**不要**改库反关账；按业务规则在本月补登，或由财务开调整单 |
| 某人不能申请（被冻结） | 超期未处理被冻结，由其直属上级在「我的团队」解冻 |
| 接口报「系统内部错误，请联系管理员」 | 程序异常：按时间在 `journalctl -u rmlm` 里找 `unhandled error` 的堆栈，连同操作步骤交给开发 |

### 附录 A：管理员调接口

页面上有的操作优先用页面。需要用接口时（手动触发定时任务、脚本化检查），先登录拿令牌（有效期 12 小时）：

```bash
read -rp '账号：' U; read -rsp '密码：' P; echo
TOKEN=$(U="$U" P="$P" python3 -c 'import json,os,urllib.request as r;q=r.Request("http://127.0.0.1:8000/api/auth/login",json.dumps({"username":os.environ["U"],"password":os.environ["P"]}).encode(),{"Content-Type":"application/json"});print(json.load(r.urlopen(q))["token"])')
```

常用接口（都要带 `-H "Authorization: Bearer $TOKEN"`，以下均为管理员可用）：

| 用途 | 请求 |
|---|---|
| 当前登录人 | `GET /api/auth/me` |
| 金蝶单据同步状态 | `GET /api/erp/docs/sync/status` |
| 立即同步金蝶单据（增量 / 全量） | `POST /api/erp/docs/sync`、`POST /api/erp/docs/sync?full=true` |
| 金蝶物料同步状态 / 立即同步 | `GET /api/master/sync/status`、`POST /api/master/sync/material?full=false` |
| 企微同步状态 / 立即同步通讯录 | `GET /api/admin/wecom/status`、`POST /api/admin/wecom/sync-contacts` |
| 手动巡检 | `POST /api/admin/jobs/tick`（见第六节） |
| 立即对账 | `POST /api/recon/run` |

例如：

```bash
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8000/api/erp/docs/sync/status
```

### 附录 B：常用 SQL

在 MySQL 里执行（`sudo -u rmlm mysql --defaults-extra-file=/etc/rmlm/backup.cnf rmlm`）。**只读查询可随时执行；写操作先备份，并在低峰期执行。**

定时任务执行记录：

```sql
SELECT name, last_key, last_run_at, LEFT(last_result, 200) AS result FROM job_run ORDER BY name;
```

管理员名下未关闭的告警待办：

```sql
SELECT t.id, u.username, t.kind, t.level, t.title, t.created_at
FROM todo t JOIN users u ON u.id = t.user_id
WHERE t.state = 'OPEN' AND t.kind IN ('JOB_FAIL', 'SYNC_FAIL', 'LOCKED_LINE')
ORDER BY t.created_at;
```

**原因排除后，手工关闭「定时任务出错」「同步失败」待办**（含已升级给上级的那几条）：

```sql
UPDATE todo SET state = 'DONE', done_at = NOW()
WHERE state = 'OPEN' AND kind IN ('JOB_FAIL', 'SYNC_FAIL');
```

> 只想关某一条时，把条件换成 `WHERE id = 待办编号`。「锁行修正」不要手工关，冲销修正后会自动关闭。

企微推送情况：

```sql
SELECT push_state, COUNT(*) FROM todo WHERE push_state IS NOT NULL GROUP BY push_state;
```

排除企微故障后，把未关闭待办里推送失败的重新排队（下一次巡检补发，每人可能一次收到多条）：

```sql
UPDATE todo SET push_state = 'PENDING', push_tries = 0 WHERE push_state = 'FAIL' AND state = 'OPEN';
```

各表大小（看数据增长）：

```sql
SELECT table_name, table_rows, ROUND((data_length + index_length) / 1024 / 1024, 1) AS mb
FROM information_schema.tables WHERE table_schema = DATABASE() ORDER BY mb DESC;
```

照片数量与总大小：

```sql
SELECT COUNT(*) AS photos, ROUND(SUM(size) / 1024 / 1024, 1) AS mb FROM photo;
```

已关账月份：

```sql
SELECT period, closed, closed_at FROM period_close ORDER BY period DESC;
```

定时任务锁是否被占用（返回 NULL 表示空闲）：

```sql
SELECT IS_USED_LOCK('rmlm_tick');
```

### 附录 C：运维相关的数据表
