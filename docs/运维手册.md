# 研发物料管家 RMLM · 运维手册（Docker Compose 部署）

- 适用：`rmlm-v1` 分支，Linux 服务器上用 Docker Compose 部署
- 读者：系统管理员（IT）
- 约定：仓库放在 `/opt/rmlm`；下文命令都**在 `/opt/rmlm` 目录下**，用有 Docker 权限的账号（root 或 docker 组成员）执行

## 速查

| 要做什么 | 命令 |
|---|---|
| 看状态 | `docker compose ps`（两个容器都是 `healthy` 即正常） |
| 看日志 | `docker compose logs -f api` |
| 启动 / 应用配置修改 | `docker compose up -d` |
| 重启 | `docker compose restart` |
| 停止 | `docker compose down`（照片在数据卷里，不会删除） |
| 手动备份 | `./deploy/backup.sh` |
| 升级 | [第八节](#八升级与回退) |
| 出故障 | [第十节](#十故障排查) |

## 一、系统概览

服务器上运行两个容器，数据库用公司独立的 MySQL 8：

```
用户浏览器 / 企微 ──HTTPS──> 反向代理（DMZ 或本机 nginx）
                                   │ http://服务器:8000
                          ┌────────┴────────┐
                          │ web 容器（nginx）│  页面 + 把 /api 转给 api
                          └────────┬────────┘
                          ┌────────┴────────┐
                          │ api 容器（后端） │  接口 + 定时任务
                          └────────┬────────┘
                                   │
                       公司 MySQL 8 · 金蝶 · 企微 · 仓储
```

| 项 | 位置 / 说明 |
|---|---|
| 程序 | `/opt/rmlm`（git 仓库） |
| 配置 | `/opt/rmlm/.env`（含密钥，权限 600，不进仓库） |
| web 容器 | 对外端口 `WEB_PORT`（默认 8000） |
| api 容器 | 不对外开放端口，只有 web 容器能访问 |
| 照片 | Docker 数据卷 `rmlm_photos`（永久保存，不能删除） |
| 数据库 | 公司 MySQL 8，库 `rmlm`。表结构在启动时自动创建、自动补列 |
| 日志 | 容器日志，每个容器最多 10 个 × 50MB，自动轮转 |
| 备份 | `/backup/rmlm` |

**必须备份的三样：数据库、照片数据卷、`.env`。**

## 二、部署

### 准备清单

| 项 | 要求 |
|---|---|
| 服务器 | Linux x86_64，2 核 4G 起；照片每张约 300KB，按此预留磁盘 |
| 软件 | Docker Engine、Docker Compose **2.24 及以上**、git |
| 数据库 | 公司 MySQL 8 上建好库和账号（第 1 步） |
| 域名与证书 | 企业已备案的 HTTPS 域名（手机扫码、企微登录都要求 HTTPS） |
| 网络 | 构建时能拉 Docker 镜像、PyPI、npm（国内可用镜像源）；运行时按需开通金蝶内网、`qyapi.weixin.qq.com`、仓储系统 |

检查 Docker 版本：

```bash
docker compose version
```

### 第 1 步：建数据库

请公司 DBA 在 MySQL 上执行。来源 IP 填 **Docker 宿主机的 IP**（容器访问 MySQL 时用的是宿主机地址）：

```sql
CREATE DATABASE rmlm DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE USER 'rmlm'@'宿主机IP' IDENTIFIED BY '数据库密码';
GRANT ALL PRIVILEGES ON rmlm.* TO 'rmlm'@'宿主机IP';
```

### 第 2 步：拉代码

```bash
git clone -b rmlm-v1 <仓库地址> /opt/rmlm
```

### 第 3 步：填配置

```bash
cd /opt/rmlm && cp .env.example .env && chmod 600 .env
```

`chmod 600`：`.env` 里有数据库密码和各类密钥，只让当前账号能读写。之后执行 `docker compose` 也用这个账号。

编辑 `/opt/rmlm/.env`，以下几项必须改：

| 配置项 | 填什么 |
|---|---|
| `DB_HOST` `DB_PORT` `DB_NAME` `DB_USER` `DB_PASSWORD` | 公司 MySQL 的地址和第 1 步的账号。`DB_HOST` 不能写 `127.0.0.1`（在容器里指容器自己） |
| `RMLM_JWT_SECRET` | 随机字符串，不填拒绝启动。生成：`python3 -c "import secrets;print(secrets.token_urlsafe(32))"` |
| `RMLM_ADMIN_PASSWORD` | 初始管理员密码（账号默认是 `admin`） |
| `RMLM_PUBLIC_URL` | 对外地址，如 `https://rmlm.example.com` |

按需填写：

| 配置项 | 说明 |
|---|---|
| `K3_*` / `WECOM_*` / `WMS_*` | 金蝶、企微、仓储，不填自动降级（[第五节](#五外部接口)） |
| `WEB_PORT` | 对外端口，默认 8000，被占用时改 |
| `NPM_REGISTRY` / `PIP_INDEX_URL` | 国内服务器构建慢时去掉注释，用国内镜像源 |

书写规则：一行一项，值后面不写注释；值里有 `$` 时用单引号包住，如 `DB_PASSWORD='a$b'`。

### 第 4 步：构建并启动

```bash
docker compose up -d --build
```

首次构建要下载依赖，约几分钟。

### 第 5 步：检查

```bash
docker compose ps
```

`api` 和 `web` 都显示 `healthy` 即成功（`api` 要能连上数据库才会变成 healthy，之后 `web` 才启动）。再确认接口：

```bash
curl -s http://127.0.0.1:8000/api/health
```

返回 `{"ok":true}` 即正常。不正常时看日志：`docker compose logs api`。

### 第 6 步：配置 HTTPS 反向代理

在 DMZ 或本机的 nginx 上，把域名转发到 `http://宿主机:8000`。示例 `/etc/nginx/conf.d/rmlm.conf`（域名、证书路径换成实际值）：

```nginx
server {
    listen 80;
    server_name rmlm.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name rmlm.example.com;
    ssl_certificate     /etc/nginx/ssl/rmlm.crt;
    ssl_certificate_key /etc/nginx/ssl/rmlm.key;

    client_max_body_size 50m;              # 上传照片、导入 Excel
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 600s;           # 金蝶全量同步、批量导入耗时较长
        proxy_send_timeout 600s;
    }
}
```

```bash
sudo nginx -t && sudo systemctl reload nginx
```

浏览器打开 `https://域名`，出现登录页即成功。

### 第 7 步：上线初始化

1. 用 `admin` 和初始密码登录，点左侧栏左下角的当前账号 →「修改密码」。
2. 系统管理 → 用户管理：建账号、勾选角色、设直属上级（可用 Excel 批量导入；启用企微时点「同步企微通讯录」）。
3. 基础数据 → 基础资料：导入项目、物料、库位、报废箱（启用金蝶时，物料点「从金蝶同步」→「全量」）。
4. 启用金蝶时：仓库作业 → ERP 单据，点「从金蝶同步领料单」。
5. 配置每日备份（[第七节](#七备份与恢复)）。
6. 用电脑和手机企微各走一遍：提交申请 → 审核 → 签收。

## 三、日常操作

### 常用命令

| 操作 | 命令 |
|---|---|
| 看状态 | `docker compose ps` |
| 实时日志 | `docker compose logs -f api` |
| 最近 1 小时日志 | `docker compose logs --since 1h api` |
| 只看错误 | `docker compose logs --since 24h api 2>&1 \| grep -iE "error\|exception\|traceback"` |
| 重启 | `docker compose restart` |
| 停止 | `docker compose down` |
| 启动 | `docker compose up -d` |
| 进入后端容器 | `docker compose exec api sh` |

- 日志里只有访问记录、警告和错误。定时任务的执行结果不写日志，查看方法见[第四节](#四定时任务)。
- 重启、停止时，最多等 10 秒让正在处理的请求完成；没跑完的定时任务会自动回滚，下次重做，不会丢数据。
- `docker compose down` 不会删除照片数据卷。**不要加 `-v`**，加了会把照片一起删掉。

### 修改配置

1. 先备份：`cp .env .env.bak`
2. 编辑 `.env`
3. 应用修改：

   ```bash
   docker compose up -d
   ```

4. `docker compose ps` 显示 healthy 即生效。

> **注意**：改了 `.env` 要用 `docker compose up -d`（会重建容器、读新配置），**`docker compose restart` 不会读新配置**。

以下配置改完后还要多做一步：

| 配置项 | 还要做什么 |
|---|---|
| `RMLM_JWT_SECRET` | 无，但所有人都要重新登录 |
| `K3_LL_BILL_TYPES`、`K3_USE_ORG` | 在 ERP 单据页做一次「全量同步」 |
| `WECOM_*`、`RMLM_PUBLIC_URL` | 同步修改企微后台的可信域名和应用主页 |
| `WMS_*` | 启用后签收必须扫仓储条码，改之前先和业务确认 |
| `WEB_PORT` | 同步修改反向代理的转发端口 |
| `RMLM_ADMIN_USER`、`RMLM_ADMIN_PASSWORD` | 只在首次启动（库里还没有账号）时生效，之后改了也没用 |
| `PHOTO_VOLUME` | 不要改，改了会换成一个空卷，历史照片打不开 |

金蝶领料单自动同步的开关和间隔在网页上改，不用重启：仓库作业 → ERP 单据 →「自动同步设置」。

## 四、定时任务

定时任务在 api 容器里全自动运行：容器启动 15 分钟后开始，之后每 15 分钟巡检一次。

| 周期 | 内容 |
|---|---|
| 每 15 分钟 | 拉金蝶领料单并生成领用行；补发企微推送；审核提醒与升级；各类超时检查；待办升级；结存异常锁行 |
| 每天（0 点后第一次巡检） | 对账；同步金蝶物料；同步企微通讯录；超期与冻结检查 |
| 每周一 | 生成报废批次 |
| 每季度第一天 | 发起长周期物料的季度在用确认 |
| 每月 1 日 | 提醒财务在 3 日前完成上月关账 |

**检查是否正常**（连接数据库见[附录 A](#附录-a常用-sql)）：

```sql
SELECT name, last_key, last_run_at FROM job_run;
```

- `daily` 行的 `last_key` 应为今天的日期；
- 启用金蝶时，`k3_docs` 行的 `last_run_at` 距现在不应超过「同步间隔 + 15 分钟」。

**不运行的常见原因**：`.env` 里的 `RMLM_SCHEDULER` 不是 `1`；api 容器在反复重启（`docker compose ps` 看运行时长）。

**手动触发**（排除故障后验证用，令牌获取见[附录 B](#附录-b调用管理接口)）：

```bash
curl -s -X POST -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8000/api/admin/jobs/tick
```

只用 `tick`：它会按周期判断，当天已执行过的任务不会重复执行。

## 五、外部接口

三个接口都是可选的，相关配置项填齐才启用，不填时自动降级：

| 接口 | 启用条件 | 不启用时 |
|---|---|---|
| 金蝶（只读） | `K3_SERVER_URL` `K3_ACCT_ID` `K3_USERNAME` `K3_APP_ID` `K3_APP_SECRET` 五项都填 | 物料、单据手工录入或 Excel 导入 |
| 企业微信 | `WECOM_CORP_ID` `WECOM_AGENT_ID` `WECOM_SECRET` 三项都填，并填 `RMLM_PUBLIC_URL` | 账号密码登录，待办只在站内显示 |
| 仓储 | `WMS_BASE_URL` `WMS_TOKEN` 两项都填 | 系统自己发 RM 码 |

改了这些配置后，用 `docker compose up -d` 应用。

### 金蝶

- **看同步状态**：仓库作业 → ERP 单据，页面顶部显示最近同步时间。
- **手动同步单据**：同一页点「从金蝶同步领料单」（增量）；旁边下拉里的「全量同步」会重新拉起始日期（默认近 3 个月）之后的单据。重复拉取不会重复入库。
- **手动同步物料**：基础数据 → 基础资料 → 物料 →「从金蝶同步」。

| 现象 | 处理 |
|---|---|
| 金蝶登录失败 | 核对账套 ID、用户名、AppID、AppSecret |
| 连接金蝶失败、超时 | 检查宿主机到金蝶服务器的网络；单据多时调大 `K3_QUERY_TIMEOUT` |
| 查询失败，提示权限不足 | 给金蝶应用账号补充查看权限 |
| 同步跳过某张单，提示已关账 | 金蝶修改了已关账月份的单据，由财务开调整单 |
| 同步跳过某张单，提示物料编码不存在 | 先同步物料，再同步单据 |
| 单据拉到了，但没生成领用行 | 属业务问题（如备注没写申请号），由领料专员在「出库开单」手工绑定 |

### 企业微信

企微后台需配置三处：应用主页填 `RMLM_PUBLIC_URL/`；网页授权可信域名填 `RMLM_PUBLIC_URL` 的域名；企业可信 IP 填服务器的出口 IP。

- 通讯录每天自动同步；需要立即同步时：系统管理 → 用户管理 →「同步企微通讯录」。
- 推送失败的消息每 15 分钟重试，3 次后放弃，站内待办不受影响。

| 现象 | 处理 |
|---|---|
| 提示「尚未开通研发物料管家」 | 用户管理 →「同步企微通讯录」 |
| 提示回调域名错误，或登录后跳到错误地址 | `RMLM_PUBLIC_URL` 与企微后台的可信域名不一致 |
| 提示 IP 不在白名单（如错误码 60020） | 在企微后台的企业可信 IP 里加上服务器出口 IP |
| 消息卡片点开打不开 | `RMLM_PUBLIC_URL` 没填，或外网访问不到 |
| 已离职的人没被停用 | 名下还有结存，系统已通知其直属上级；清零后，下次同步时自动停用 |

### 仓储

| 现象 | 处理 |
|---|---|
| 提示「仓储系统暂时连不上」 | 检查网络和仓储服务；响应慢时调大 `WMS_TIMEOUT` |
| 提示返回格式不正确、新码数量不符 | 仓储接口与[仓储接口规范](仓储接口规范.md)不一致，找仓储方排查 |

## 六、巡检

建议接入公司监控：每分钟探测 `https://域名/api/health`，连续 3 次失败时告警；磁盘使用率超过 80% 时告警。

### 每天

1. `docker compose ps`：两个容器都是 healthy。
2. 用管理员账号看「我的待办」，处理「定时任务出错」「同步失败」「锁行修正」「冲销复核」。
3. 启用金蝶时，ERP 单据页的最近同步时间正常。
4. 昨晚的备份成功：`tail -1 /backup/rmlm/backup.log` 显示「备份完成」。

### 每周

1. 检查定时任务（[第四节](#四定时任务)）。
2. 检查磁盘：`df -h / /backup`；Docker 占用：`docker system df`。
3. 抽查审计日志（系统管理 → 审计日志），看有没有大量失败请求（状态码 401、403、500）。

### 每月

1. 1–3 日：把「冲销复核」全部处理完，否则财务无法关账。
2. 清理升级留下的旧镜像：`docker image prune -f`。
3. 安装系统和 Docker 补丁，在低峰期进行。

### 每季度

1. 做一次恢复演练（[第七节](#七备份与恢复)）。

> **注意**：「定时任务出错」「同步失败」两类待办处理完后**不会自动消失，页面上也关不掉**。如果不手工关闭，48 小时后会升级给上级，3 天后通知研发副总。处理完后，用[附录 A](#附录-a常用-sql) 的 SQL 关闭。

## 七、备份与恢复

### 配置每日备份（只需做一次）

仓库自带备份脚本 `deploy/backup.sh`：从公司 MySQL 导出数据库、从 api 容器拷出全部照片，存到 `/backup/rmlm/日期/`，保留 30 天。

**第 1 步**：建备份目录，手动执行一次：

```bash
mkdir -p /backup/rmlm && ./deploy/backup.sh
```

输出「备份完成」，并且 `/backup/rmlm/当天日期/` 下有 `rmlm.sql.gz` 和 `photos` 目录。

**第 2 步**：设置每天 2:30 自动执行：

```bash
crontab -e
```

在打开的文件里加一行：

```
30 2 * * * /opt/rmlm/deploy/backup.sh >> /backup/rmlm/backup.log 2>&1
```

**第 3 步**：用公司备份系统把 `/backup/rmlm` 同步到异地；`.env` 单独加密保存一份。

- 公司 DBA 已在备份 `rmlm` 库时，把定时任务里的命令改成 `SKIP_DB=1 /opt/rmlm/deploy/backup.sh`，只备份照片。
- 每份备份都含全部照片，`/backup` 的磁盘按「照片总量 × 30」预留。
- 脚本要在 api 容器运行时执行（连接参数从 api 容器读取）。

### 恢复

1. 停止服务：

   ```bash
   docker compose down
   ```

2. 恢复数据库：请公司 DBA 把备份导入 `rmlm` 库。宿主机装有 mysql 客户端时也可以自己导（日期换成要恢复的那天）：

   ```bash
   gunzip -c /backup/rmlm/2026-11-27/rmlm.sql.gz | mysql -h 数据库地址 -u rmlm -p rmlm
   ```

3. 启动服务：

   ```bash
   docker compose up -d
   ```

4. 恢复照片，并把属主改回程序账号：

   ```bash
   docker compose cp /backup/rmlm/2026-11-27/photos/. api:/data/photos/
   ```
   ```bash
   docker compose exec -u root api chown -R appuser:appuser /data/photos
   ```

5. `docker compose ps` 显示 healthy 后，登录抽查台账和照片。
6. 通知业务：备份时间点之后的操作需要补登（金蝶单据会在下次同步时自动补回）。

### 恢复演练（每季度）

在测试服务器上拉同一版本的代码，按上面的「恢复」步骤把备份导入**测试库**。测试服务器的 `.env` 必须设置 `RMLM_SCHEDULER=0`，并清空 `WECOM_*`、`K3_*`、`WMS_*`，否则会给真实用户推送消息。登录后抽查几条台账和照片能否打开。

## 八、升级与回退

### 升级

选低峰时段，避开 0 点前后和每月 1–3 日（关账期）。构建期间服务照常运行，切换新容器时中断约 1 分钟。

1. 备份：

   ```bash
   ./deploy/backup.sh
   ```

2. 记下当前版本号（回退时要用）：

   ```bash
   git rev-parse --short HEAD
   ```

3. 拉取新代码：

   ```bash
   git pull --ff-only origin rmlm-v1
   ```

4. 检查有没有新增配置项（把「旧版本号」换成第 2 步的输出），有的话补到 `.env`：

   ```bash
   git diff 旧版本号 HEAD -- .env.example
   ```

5. 重新构建并启动：

   ```bash
   docker compose up -d --build
   ```

6. 验证：
   - `docker compose ps` 两个容器都是 healthy；
   - `docker compose logs --since 5m api` 里没有报错；
   - 浏览器刷新后能登录，能打开领用台账和 ERP 单据页。

表结构变更在启动时自动完成，不需要手工操作。

### 回退

1. 切回旧版本：

   ```bash
   git checkout 旧版本号
   ```

2. 检查新版本有没有改表结构：

   ```bash
   git diff 旧版本号 rmlm-v1 -- backend/app/models.py
   ```

   有输出时，先 `docker compose down`，再请 DBA 用升级前的备份恢复数据库；没有输出时跳过这一步。
3. 重新构建并启动：

   ```bash
   docker compose up -d --build
   ```

4. 验证（同升级第 6 步）。
5. 问题修复后回到最新版本：先执行 `git checkout rmlm-v1`，再重新走一遍升级流程。

## 九、账号与安全

### 账号

| 场景 | 操作 |
|---|---|
| 新建账号 | 用户管理 → 新建。不填密码时，初始密码为 `Rmlm@123456` |
| 批量导入 | 用户管理 → 导入 Excel，初始密码同上 |
| 重置密码 | 用户管理 → 编辑 →「重置密码」。保存后，此人已登录的设备全部下线 |
| 停用（离职、调岗） | 用户管理 → 编辑 → 关闭「启用」。名下还有结存等未清事项时不能停用，按提示先清零 |
| 解冻 | 只能由其直属上级在「我的团队」里解冻 |

**管理员忘记密码，且没有其他管理员时：**

1. 生成新密码的哈希值（按提示输入新密码）：

   ```bash
   docker compose exec api python -c "import bcrypt,getpass;print(bcrypt.hashpw(getpass.getpass('新密码：').encode(),bcrypt.gensalt(10)).decode())"
   ```

2. 请 DBA 在数据库里执行，把哈希值换成上一步的输出：

   ```sql
   UPDATE users SET password_hash='哈希值', token_version=token_version+1, active=1 WHERE username='admin';
   ```

### 安全要点

- `.env` 权限设为 600；密钥不外传，不提交到仓库。
- 对外只开反向代理的 443 端口。`WEB_PORT` 只允许反向代理访问——Docker 映射的端口**不受 ufw 等主机防火墙限制**，要在安全组或网络防火墙上限制。
- docker 组成员等同于 root，只给运维人员。
- 系统没有登录失败锁定，外网访问必须经过 DMZ 代理。
- 怀疑登录令牌泄露时：更换 `RMLM_JWT_SECRET`，执行 `docker compose up -d`，所有人需重新登录。
- 业务数据只能通过页面修改；账目有错时走「冲销」流程，不要直接改数据库。

## 十、故障排查

先看两样：`docker compose ps` 和 `docker compose logs --tail 100 api`。

| 现象 | 处理 |
|---|---|
| 启动时提示「请在 .env 中设置 RMLM_JWT_SECRET」 | 在 `.env` 里填 16 位以上的随机字符串 |
| 启动时提示 `env_file` 格式不认识 | Docker Compose 版本太旧，升级到 2.24 及以上 |
| 构建时拉取镜像或下载依赖失败 | 配置 Docker 镜像加速或公司镜像仓库；`.env` 里设 `NPM_REGISTRY`、`PIP_INDEX_URL` |
| 提示端口已被占用（port is already allocated） | 改 `.env` 的 `WEB_PORT`，同步改反向代理 |
| api 一直不是 healthy、web 没启动 | api 连不上数据库：`DB_HOST` 是否写成了 `127.0.0.1`；DBA 授权的来源 IP 是否为宿主机 IP；防火墙 |
| 改了 `.env` 不生效 | 用了 `docker compose restart`，改用 `docker compose up -d` |
| 升级后页面空白 | 浏览器强制刷新 |
| 接口报 502 | api 容器没在运行或不健康 |
| 接口报 504（如金蝶全量同步） | 反向代理（含 DMZ）的 `proxy_read_timeout` 设为 600s |
| 上传照片、导入 Excel 报 413 | 反向代理（含 DMZ）的 `client_max_body_size` 设为 50m |
| 历史照片打不开 | `.env` 的 `PHOTO_VOLUME` 被改过，改回原卷名；必要时从备份恢复照片 |
| 上传照片失败（恢复照片后） | 照片属主不对，执行恢复第 4 步的 `chown` 命令 |
| 手机扫码打不开摄像头 | 必须用 HTTPS 访问 |
| 磁盘快满 | `docker image prune -f` 清旧镜像；检查 `/backup` 是否同步到异地后可清理 |
| 提醒、同步都不动了 | 见[第四节](#四定时任务)「不运行的常见原因」 |
| 领导收到「【二级】」「【三级挂账】」开头的同步失败提醒 | 管理员没关闭已处理的告警待办，见[附录 A](#附录-a常用-sql) |
| 关账时提示有待复核的冲销 | IT 到 对账与关账 →「冲销」页签复核 |
| 关账时提示差额不为 0 | 由业务处理差异；系统不支持反关账，不要改数据库 |
| 页面提示「系统内部错误」 | 按发生时间在 `docker compose logs api` 里找 `unhandled error`，连同操作步骤一起交给开发 |
| 金蝶、企微、仓储相关报错 | 见[第五节](#五外部接口) |

## 附录 A：常用 SQL

用公司常用的 MySQL 客户端连接 `rmlm` 库执行，或交给 DBA 执行。查询可以随时执行；修改数据前先备份。

**定时任务执行记录**

```sql
SELECT name, last_key, last_run_at FROM job_run;
```

**未关闭的告警待办**

```sql
SELECT id, kind, title, created_at FROM todo
WHERE state = 'OPEN' AND kind IN ('JOB_FAIL', 'SYNC_FAIL') ORDER BY created_at;
```

**关闭已处理的告警待办**（「定时任务出错」「同步失败」）

```sql
UPDATE todo SET state = 'DONE', done_at = NOW()
WHERE state = 'OPEN' AND kind IN ('JOB_FAIL', 'SYNC_FAIL');
```

**企微推送统计**（`FAIL` 表示 3 次都失败、已放弃）

```sql
SELECT push_state, COUNT(*) FROM todo WHERE push_state IS NOT NULL GROUP BY push_state;
```

**企微故障排除后，重新推送失败的消息**

```sql
UPDATE todo SET push_state = 'PENDING', push_tries = 0 WHERE push_state = 'FAIL' AND state = 'OPEN';
```

**各表占用空间**

```sql
SELECT table_name, ROUND((data_length + index_length) / 1024 / 1024, 1) AS mb
FROM information_schema.tables WHERE table_schema = DATABASE() ORDER BY mb DESC;
```

## 附录 B：调用管理接口

页面上能做的优先在页面上做。确实需要调接口时（地址里的 8000 换成 `WEB_PORT`）：

**第 1 步：获取令牌**（有效期 12 小时）

```bash
read -rp '账号：' U; read -rsp '密码：' P; echo
TOKEN=$(U="$U" P="$P" python3 -c 'import json,os,urllib.request as r;q=r.Request("http://127.0.0.1:8000/api/auth/login",json.dumps({"username":os.environ["U"],"password":os.environ["P"]}).encode(),{"Content-Type":"application/json"});print(json.load(r.urlopen(q))["token"])')
```

**第 2 步：调用接口**，例如查看金蝶同步状态：

```bash
curl -s -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8000/api/erp/docs/sync/status
```

| 用途 | 方法与地址 |
|---|---|
| 手动巡检 | `POST /api/admin/jobs/tick` |
| 金蝶单据同步状态 | `GET /api/erp/docs/sync/status` |
| 金蝶单据增量 / 全量同步 | `POST /api/erp/docs/sync`、`POST /api/erp/docs/sync?full=true` |
| 金蝶物料同步 | `POST /api/master/sync/material` |
| 企微通讯录同步 | `POST /api/admin/wecom/sync-contacts` |
| 立即对账 | `POST /api/recon/run` |
